Chat & email marketing — deep review

I read the full stack this time — schema, services, routes, hooks, shared chat-ui package, both frontends. The honest summary: the chat system is ~85% built and well-built — batched queries, SSE fan-out, DB-clock read receipts, soft-delete, forwards, mentions, presence. What's missing is mostly the last 15%: columns that exist with no writers, routes that exist with no callers, links that point at pages that don't exist. Marketing is the inverse — a real lifecycle engine (draft → scheduled → sent, per-recipient ledger, delayed BullMQ jobs) behind a UI that only knows how to press "Send" — plus two outright lies: an SMS channel that sends email, and merge fields that are never merged.

Findings — ordered by severity

FindingEvidence
Bug Every chat notification and offline-reply email links to /chat?conversation=… — a route that does not exist in the ops app. Clicking "Ama sent you a message" in the bell, or the link in the offline email, lands on the catch-all. The single most-clicked chat link goes nowhere. chat.ts:716 link: "/chat?conversation=" · chat.ts:1169 same in emails · App.tsx routes: no /chat
Bug "Closed" can never happen. The status/closedAt columns and the enum exist; the helpdesk renders a Closed band and per-row status — and zero code paths write either field. Resolved threads sit in "awaiting" forever; wait-time stats inflate; the queue only ever grows. schema.ts:1529 columns exist · serializer reads (row as any).status (the cast is the tell) · no route mutates it
Bug "Mine" is semantically broken. Opening a support thread auto-joins you as a participant (ensureSupportQueueAccess) — so merely reading a conversation makes it "mine". The filter quietly accumulates every thread you've ever opened; there is no real ownership. chat.ts:319-351 auto-join · helpdesk isMine checks participants
Dead pipe Attachments are plumbed end-to-end except the two ends. Table ✓ · attachmentIds binding with correct ownership scoping ✓ · MessageBubble renders them ✓ · upload endpoint ✗ · paperclip in Composer ✗. Eighty percent built, unreachable. schema.ts:1638 · sendMessageInternal:604-615 · MessageBubble.tsx:384 · no upload route in chat.ts
Dead pipe No staff-only notes. Every message in a client thread goes to the client. "Spoke on the phone, reissued invoice" can't be recorded where it happened — staff will keep notes in WhatsApp instead, and the thread loses the story. messages table has no visibility flag; one composer mode

Gap No message search anywhere. Directory search finds people; nothing finds what was said. Routes paginate by cursor only. no ?q= in chat.ts routes
Gap The hub is a 360px floating box. Fine for a reply, wrong for reading a 40-message case thread over the case itself. All components are already shared — a full page is a route, not a build. CommunicationHub fixed-position only

II · Chat — the proposal

Ordered by leverage. P1–P3 are what make the helpdesk an actual helpdesk; P4–P6 finish pipes that are already laid.

P1
Resolve / reopen — one route, both surfaces.
PATCH /chat/conversations/:id/status {open|closed}, restricted to support-queue roles. Closing writes status+closedAt, posts a type:"system" message ("Resolved by K. Mensah" — the type exists), and publishes SSE. A new client message auto-reopens. Thread header gets Resolve ✓ / Reopen; rows show resolved · K.Mensah · 2d ago; the Closed band finally fills. Portal renders the system message as a divider.
route + 2 UI touches
~½ day
P2
Ownership via the role that already exists. No schema change — conversationParticipants.role already has owner. Claim = set my row to owner, demote any existing owner to member.
First staff reply into a client-facing thread auto-claims. Rows get an owner pill; "Mine" filters on ownership instead of "ever opened it"; auto-join stops lying. Reassign = a participant-picker in the thread head reusing POST /participants.
service fn + list field
~½ day
P3
Client context rail in the thread. One new aggregate endpoint — GET /chat/conversations/:id/context returning the linked applicant's stage, branch, balance state, and next appointment.
Renders as a right-hand column in the helpdesk split. Kills the open-the-case-in-another-tab dance that every reply currently needs.
aggregate route + rail
~½–1 day
P4
Internal notes — one column. messages.visibility: public|internal. Composer gains a Reply/Note toggle; internal rows render as dashed mono strips and — the important half — getApplicantMessages and the client SSE payload filter them out.
Care point: the broadcast path must never leak internal notes to the client channel. The split is already natural — staff SSE vs the portal's own fetch.
migration + serializer + UI
~1 day
P5
Finish the attachment pipe. POST /chat/attachments → presigned R2 put (same storage service as documents) → staged row; send binds via the existing attachmentIds path. Paperclip in Composer; the bubble already renders them. Portal gets it too — "screenshot of your receipt" is half of all support volume.

~1 day
P6
/chat full page + search. A route that renders the hub's split at page width (list | thread), reading ?conversation= — instantly fixing every dead notification/email link. Add ?q= ILIKE on the messages route; search box in helpdesk + the page.
page + query param
~1 day
P7
Client widget passes. Square launcher + window, badge to hollow-ink, drop the green dot. "Seen HH:MM" under the client's last bubble — deliveryStatus is already computed per-viewer, just not rendered on this surface.

III · Email marketing — what's actually true

The engine is real; the cockpit is fake

POST /campaigns → draft  ·  POST /:id/send {scheduleFor?} → snapshotRecipients → BullMQ(delay)
PATCH /:id (edit draft/scheduled)  ·  cancelQueuedCampaignSend  ·  GET /:id/recipients (per-contact ledger)
worker runCampaignSend → per row: personalize → unsubscribe URL → emailLayout → sendEmail → sent/failed+error
lists + contacts (pending→confirmed double opt-in)  ·  import leads/applicants  ·  templates CRUD + preview
FindingEvidence
Lie SMS sends email. runCampaignSend calls Resend's sendEmail for every recipient with no channel branch. A "Deadline Warning · SMS · 96 delivered" campaign either emailed 96 people or failed silently — and there's a whole /marketing/sms route pointing at this page plus three SMS templates selling the fiction. marketing.ts:195-259 — no channel check anywhere
Lie {{date}} and {{intake}} are advertised and never merged. The compose hint promises them; the worker replaces only {{name}}/{{Name}}. Every campaign using them ships literal {{date}} to applicants. marketing.ts:223-228 two replaces vs the UI hint "Use {{name}}, {{date}}, {{intake}}"
Unreachable Scheduling is fully built — and the UI can't reach it. scheduleFor → delayed BullMQ job → scheduled status → cancelQueuedCampaignSend. The page exposes none of it: no datetime, no Scheduled rows, no cancel. routes/marketing.ts:280 + queues.ts:255-274 vs compose form
Unreachable No draft workflow despite draft status + PATCH existing. The form does POST /campaigns then immediately POST /send — one atomic click. You cannot write a campaign today and send it tomorrow without leaving it half-typed in a tab. handleSend — create→send in one confirm
Unreachable The per-recipient ledger is returned by the API and never displayed. "Failed: 8" is a dead number — can't see who, can't see why (error is stored per row!), can't retry. And re-sending re-snapshots the whole list — there is no path that retries only failures without re-emailing the delivered. GET /campaigns/:id/recipients — zero callers in the page
Gap No test send, and compose has no preview — though the template editor does. First time anyone sees the real email is when 400 contacts do. compose = raw textarea; emailLayout could render a true preview
Gap No opens/clicks. The webhooks router is Paystack-only; Resend events (delivered/opened/bounced) could feed campaign_recipients — also gives you bounce-suppression for free. routes/webhooks.ts — paystack only
Polish Colour leaks: green delivered/SMS, red failed, blue channel badges and --primary accents — against a console that's otherwise strict mono. stats cards + table cells + compose border
Note Genuinely good: double opt-in newsletter flow, unsubscribe tokens on every send, snapshot-at-enqueue semantics (list changes after scheduling correctly don't apply), contacts filters/search/import. The bones justify finishing it. newsletter.ts, contact management UI
IV · Marketing — the proposal

M1–M2 are honesty fixes — stop the page promising what the backend can't keep. M3–M6 wire up what's already built.

M1
SMS: decide, don't pretend. Option A (recommended now): remove the channel — picker, presets, /marketing/sms route, and treat existing "SMS" campaigns as what they were: email. Option B (when there's an actual provider): wire Arkesel/mNotify behind if (channel === "SMS") in runCampaignSend + a settings key. ~30 lines when the day comes — but not before there's an account to send from.
A: ~1 hour
B: when real
M2
Merge fields: promise what's replaced. Implement {{date}} (send date — trivial) and add {{email}}; remove {{intake}} — there's no per-recipient intake to merge. Show the available fields beside the editor, live.
~1 hour
M3
The lifecycle UI. Compose footer becomes Save draft · Send test · Send now / Schedule ▸. Draft rows get Edit/Delete; scheduled rows get Edit/Cancel (calls the existing cancel); sent rows get Report/Duplicate. Status column uses pills — DRAFT · SCHEDULED Oct 1 09:00 · SENDING · SENT — not a bare word.
UI only — API exists
~1 day
M4
Delivery report drill-down. Expand a sent row → the existing /recipients route → per-contact delivered · opened · failed — {error} + a "Retry failed" action.
Retry needs one small addition: re-enqueue must not re-snapshot the list — filter the existing ledger to failed rows instead of deleting and rebuilding it.
row expand + retry branch
~1 day
M5
Test send + true preview. POST /campaigns/:id/test {email} — runs the real personalize+layout path for one address. Preview toggle renders emailLayout server-side (a tiny render route), so what you see is what 400 people get — not a lookalike.
2 small routes + UI
~½ day
M6
Resend webhook → opens + bounce suppression. /webhooks/resend verifies the svix signature, maps events to campaign_recipients.openedAt/bouncedAt (two new columns), feeds an Opened column in the table — and bounced addresses get skipped by future sends. Phase 2, but it's where the channel becomes measurable.
webhook + columns
~1 day

Mono pass on the stats/table/badges, and the empty state says "No campaigns yet" only when that's true (drafts aren't "sent yet").
½ hour
V · Suggested order — one coherent push
Phase 1 — honesty (½ day): M1 hide SMS · M2 merge-field truth · M6-sweep lastMessageAt/as-any. Everything here is a deletion or a two-line fix that stops the system lying.

Phase 2 — the helpdesk becomes a helpdesk (~1½ days): P1 resolve/reopen · P2 ownership · P6's /chat page (the dead-link fix alone justifies it) · P3 context rail.

Phase 3 — marketing cockpit (~2 days): M3 lifecycle UI · M4 ledger + retry · M5 test send.

Phase 4 — depth (as needed): P4 internal notes · P5 attachments · P7 widget restyle · M6 opens webhook.

Everything above Phase 4 needs no new tables — P4's visibility flag and M6's two recipient columns are the only migrations in the whole set. The schema, the queues, and the routes already believed in these features; the work is connecting them.
