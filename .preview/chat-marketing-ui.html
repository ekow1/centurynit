How contacts get in — four doors, all mapped to existing or tiny API work:
  • One by one — the current name+email form, tucked behind a button instead of always-on. New contacts default to pending and get the confirmation email (double opt-in stays).
  • Paste a list (new) — textarea accepts one-per-line or Name <email>; the client parses, shows n parsed · m duplicates, then bulk-adds. Needs one bulk route (or a client-side loop over the existing single-add endpoint) — the dedupe-by-email logic already exists server-side.
  • Import from leads / applicants — the existing endpoints; the row reports the result honestly (84 added · 12 already on list instead of a bare toast). Snapshot semantics stay — it's a copy, not a live segment.
  • The newsletter list fills itself — public /newsletter/subscribe → pending → confirm-link → confirmed. It's flagged, can't be renamed.
Per-status actions match reality: pending → Resend confirm / Confirm now (manual override, already an endpoint) / Remove · confirmed → Unsubscribe / Remove · unsubscribed → Remove only. And Send to list on the card jumps to compose with the audience pre-selected.
