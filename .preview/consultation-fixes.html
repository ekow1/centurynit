A · the recovery model — needs your call

The problem

Reopen as built is a dead end. It flips the case to Under Review but the slot is gone — ops can't attach a new one (reschedule refuses a cancelled booking), and the portal sees an active case, so the client gets the case view with "Unscheduled" and no way to book. Reopened = stuck on both sides.

Option A — recommended · cancelled is terminal, recovery is a linked new case

"Reopen case" goes away. The one recovery action is Issue free rebooking — or nothing, if the client should simply pay again.

  • Credit issued → client notified → they pick a slot → a new consultation opens, linked back via rebooked_from_id.
  • The cancelled row stays as history — one story, two linked records.
  • Ops-mistake cancel → issue the credit. Client's own cancel → no action; they rebook and pay.
  • No zombie states. Nothing to get stuck on.

Option B — reopen resumes the same case file

Reopen + client picks a new slot into the same consultation row — comments, doc requests and history stay in one file.

  • Checkout detects the reopened case and attaches the new booking (consultations.booking_id is rewritten).
  • Portal needs a "pick a slot" state inside an active case — the case view embeds the picker when there's no booking.
  • Fee still applies unless credited — same credit flag.
  • Cost: touches checkout, ensureCaseForBooking, portal case view, and the booking↔case link. 2–3× the work of A.
Recommendation: A. A cancelled case is a receipt, not a draft — the audit trail is cleaner when the replacement is a new linked record, and nothing in the current ops workflow needs the old row to come back to life. The mock below assumes A; if you want B, say so and the §B card keeps a "Reopen" that means "client picks a slot into this file".
