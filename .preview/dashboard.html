The dashboard, rebuilt

Three problems on the current page: it asks you to confirm a consultation you already booked (the "confirm" pending-action misfires — see the bug note below), it tells you where you are three separate times (status band, six-tile strip, "Now" section), and the right rail is four disconnected cards when the applicant only asks one question: what happens next?

The bug — why "Confirm" is still there

Root cause

The moment you pay for a consultation, completeConsultationPayment() sets consultationPhase = "awaiting_confirmation". The pending-action resolver reads that phase and emits title: "Confirm your consultation" — an action aimed at you. But confirming a slot is a staff-only operation (confirmConsultationSlot requires an assigned consultant and a meeting link). The sync only moves the phase forward when the case reaches CONFIRMED/slotConfirmed on the server. So between "you booked" and "a consultant confirms", the dashboard orders you to do a thing you cannot do.

Fix in the mock: that state renders as status, not action — "Booked — the branch is confirming your slot" with the appointment inline. A client-facing Confirm only appears when a staff-proposed reschedule genuinely waits on the applicant (a distinct flag), never on the normal booked path.

Mobile rules

  • Refs hide on phones — the consultation ref lives on the appointment block; APP id is in the ledger and profile. Header stays one line.
  • Band stacks vertically, button goes full-width (~44px target) — one thumb tap, no side-scrolling text next to a button.
  • Rail wraps 3×2; locked chapters collapse to bare numerals — you don't need "Locked" read to you five times on a small screen.
  • Needs-you card comes first in the single-column flow — the actionable thing lands above the fold, before money/people/updates.
  • Status tags compact ("$150 DUE", "BOOKED") — the date detail moves into the row title or a tap-through.
  • Updates clamp at 3 lines with the `+N more` expander the component already ships.
  • Breakpoint is the shell's own 960px — these are the same rules the page will get in app.mobile.css.

What changes in code

Fixes (the confirm bug)

  • getPendingAction: drop the awaiting_confirmation → "Confirm your consultation" action. It becomes a status the band renders read-only. A client confirm action returns only if a real applicant-side decision exists (e.g. accepting a proposed reschedule — needs a server flag like slotProposedBy: "staff").
  • Hero refs: resolve the consultation ref from liveConsultation.reference first, fall back to booking.confirmationId. Never show "Not booked" while a live case exists.
  • completeConsultationPayment setting awaiting_confirmation is semantically fine — the error is only that the pending-action layer treated a staff-side wait as a client-side task.

Structure (DashboardHome.tsx)

  • One <StatusBand>: pendingAction → action skin; else derived status (booked/confirming, next dated thing, or idle). Replaces action-now/journey-now + the appointment card.
  • jmini six-tile strip → slim n-rail (same data, chapterStateOf unchanged).
  • "Now" section → "Needs you" list fed by pending action + dueList invoices + rejected docs already in state.
  • Rail merges money/people/documents into one card; updates card (already rebuilt) stays.
  • No API changes. Everything is client-side regrouping + the two correctness fixes.
