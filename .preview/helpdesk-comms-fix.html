Helpdesk + portal chat - bugs found in the live code

One thread model, three broken seams

Click things - the portal widget and the ops queue are live mock state.

What the code actually does today5 confirmed
1 · Staff replies never reach the open chat The API publishes chat.message to staff participants only - the client gets a chat.reply notification the widget doesn't handle. Client must close + reopen to see replies. Fix: publish the message to conv.userId too - the existing SSE case renders it live.
2 · "X replied" notification → dead page The client's in-app notification links /portal/support - a route that was deleted. Click → 404/fallback, chat doesn't even open. Fix: /portal?chat=open + the launcher reads the param and opens.
3 · Client messages can black-hole Case/stage threads with zero staff participants are invisible in the queue (bypass is support-only) and notify nobody (fallback is support-only). A deleted consultant's case thread goes dark. Fix: queue + fallback cover every client-facing type.
4 · "Awaiting reply" lies to queue staff awaiting = clientLastMsg || myUnread>0 - for non-participant queue roles unread = entire history, so everything shows awaiting forever, and a colleague's reply still counts. Wait-timers inherit the lie. Fix: awaiting = client wrote last. Unread is a separate badge.
5 · Queue fetches every message ever sent listConversations selects all messages of all conversations to pick the latest per thread - O(history) per refresh. Fix: DISTINCT ON - one row per conversation.
