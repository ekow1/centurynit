Helpdesk, chat & email marketing — reviewed

Three areas, one pass. The verdict up front: the chat substrate is genuinely good — one thread model, shared century-nit-chat-ui components, SSE typing, quotes, reactions. The gaps are at the edges: a helpdesk where nothing can ever be closed, a marketing page offering an SMS channel the backend cannot send, and scheduling + per-recipient delivery routes that exist in the API but are never called from the UI. Sections A–D show each fix as a mock.

A · Ops helpdesk — the triage surface can't finish a job

What I found in the code

FindingWhere / evidence
"Closed" is a band that can never have rows. The queue renders closed/archived conversations — but no endpoint sets that status, and no button calls it. Resolved threads stay "awaiting" forever and the waiting-time stats inflate. chat.ts routes: no status endpoint. EnterpriseHelpdesk: renders isClosed() rows, offers no close action.
"Mine" filters on a thing nobody can set. The chip checks whether I'm in participants — but participants are whoever's posted, not an owner. There's no claim/assign affordance, so two staff can answer the same thread blind. isMine() → participants.some(p.opsUserId === me). POST /conversations/:id/participants exists but helpdesk never calls it.
No client context. The thread header gives a name and a kicker. To know which applicant this is — stage, branch, open balance, next booking — staff leave the page and hunt. Thread head: kickerOf + clientName only. entityLink gives an "Open case →" escape, not context.
No internal notes. Every keystroke goes to the client. Staff can't annotate a thread ("spoke on phone, sending revised invoice") without the applicant seeing it. Composer has one mode: send. Messages have no internal flag.
No canned replies. "Your invoice is at /portal/financial" gets typed a hundred times a week. —

Four additions, all small:
  • Resolve / Reopen — a PATCH /conversations/:id/status endpoint (schema already carries the status) + a header button. Resolving folds the thread into the Resolved band and drops it out of "awaiting" stats; a new client message re-opens it automatically (the divider marks it in-thread).
  • Claim / Reassign — first staff reply auto-claims (adds a real assigneeOpsUserId, distinct from participants). Rows show the owner; "Mine" finally means something. Reassign reuses the participants endpoint.
  • Context rail — right column resolves the linked applicant once: stage, branch, balance, next appointment. One extra lookup on open; kills the tab-hopping that triage currently needs.
  • Reply ⇄ Note toggle — a visibility: "internal" flag on the message; renders as a dashed mono strip (above), never leaves the staff surface. Snippet chips insert saved replies.

  • Colour leaks — the green presence dot (#10b981) and red unread badge (#dc2626) are the only saturated pixels in the entire portal. Badge → hollow-square ink on white; presence dot → ink square (or drop it — the portal has no presence concept anyway).
  • Shape — 56px circle + 16px-radius window vs. the square command-center system everywhere else. Square launcher with the hard drop shadow, square window, mono header — matches the modal/pill language.
  • Resolution is visible to the client — when ops resolves a thread (§A), the client sees the divider ("Resolved · who · when") and the next message starts a fresh segment. One permanent thread stays the model — but it stops reading as an endless unbounded stream.
  • Read state — staff already get markRead; echo it client-side as a mono "Seen 14:02" under the last own bubble. One field, ends "did anyone see this?" follow-ups.
  • Attachments — applicants constantly need to send a screenshot/receipt. The composer has no attach path; a paperclip that drops the file into the thread (same storage as the vault) closes the loop.
C · Staff chat hub — already strong; two small adds
The internal hub (presence, DM, groups, forward, reactions, typing) is the most complete of the three surfaces. Two gaps worth the small cost:
  • No full-page view. The floating window is fine for a quick reply but unusable for a long case discussion — it covers the record you're discussing. A /chat route rendering the same hub full-width (like Helpdesk's split) costs almost nothing — the components are already shared.
  • No message search. The directory search finds people; nothing finds what was said. The API already paginates messages — a search box over a ?q= query is additive.
D · Email marketing — the page promises more than the API keeps

What I found in the code

FindingWhere / evidence
SMS is a dead channel — worse, it's a lie. The channel picker and three SMS templates exist, but runCampaignSend calls Resend's sendEmail unconditionally. An "SMS campaign" would email the contact list — or fail confusingly. Nothing SMS-shaped exists anywhere in the worker. marketing.ts:240 — sendEmail({…}) for every recipient; no provider branch on channel.
Scheduling is built and unreachable. POST /campaigns/:id/send accepts scheduleFor, BullMQ takes a delayed job, cancelQueuedCampaignSend exists — and the UI has exactly one button: "Send". No datetime picker, no Scheduled status, no cancel. routes/marketing.ts send route + worker queues vs. EnterpriseCampaigns compose form.
No draft state in practice. Create → send is one atomic click. The API's PATCH /campaigns/:id ("edit a draft/scheduled campaign") is never called — you can't prepare a send and review it later. handleSend does POST /campaigns then immediately POST …/send.
The delivery ledger is invisible. GET /campaigns/:id/recipients returns per-contact sent/delivered/failed — the page never calls it. "Failed: 3" is a dead number; you can't see who failed or retry them. Route exists; zero references in the page.
No test send. First time you see the email is when 400 contacts do. No "send to me" — and the body editor is raw HTML in a textarea, no rendered preview. Compose form — no preview toggle, no test action.
Colour leaks — green #10b981 delivered/SMS counts, red #ef4444 failed, --primary blue accents. The rest of the console is strict mono. Stats cards + status cell + compose card border.

Compose — the send button becomes a lifecycle

Send NowAt —

  • SMS — be honest about it. Two options: (a) hide the channel until a provider exists (one line — remove it from the picker and the SMS presets), or (b) actually wire one — Arkesel or mNotify are the Ghana-standard REST APIs, ~30 lines in runCampaignSend behind if channel === "SMS" plus a settings key beside the others. Pick (a) now, (b) when there's budget/need.
  • Scheduling is free — scheduleFor + delayed BullMQ job + cancel all exist. The UI work is the Now/At toggle, a Scheduled pill, and an Edit/Cancel action on scheduled rows.
  • Draft → test → send — "Save draft" creates without enqueueing (the API already supports it); "Send test to me" needs one small route that runs the personalise+layout path for a single address. Rendered preview toggle reuses emailLayout verbatim — it already exists server-side.
  • Ledger drill-down — expandable row calls the existing /recipients route; "retry failed" re-enqueues only failed rows (the snapshot already tracks per-row status).
  • Opens — Resend can report opens via webhook; a /webhooks/resend consumer flipping recipient openedAt feeds the Opened column. Optional — say the word and it's in.
  • Mono pass — delivered/failed become ratios in ink; failed rows get a dashed pill, not red.
Order I'd suggest
1. SMS honesty (one-line hide, or provider)  →  2. Helpdesk resolve + claim (the queue is un-actionable without it)  →  3. Campaign lifecycle UI (draft/schedule/ledger — all API exists)  →  4. Context rail + notes  →  5. Client widget restyle  →  6. Full-page staff chat + search.
