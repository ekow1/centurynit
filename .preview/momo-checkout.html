Why the split

MoMo is fully ours. POST /charge takes mobile_money:{phone,provider} — no card data, no PCI scope, so the whole screen can be Century NIT's. The "approve on your phone" state is a better UX than Paystack's generic hosted page, which shows the same waiting state anyway after a redirect.

Cards stay inside Paystack's modal. A hand-rolled card form would push PAN/CVV through our API — PCI DSS SAQ D, a real compliance program, for pixels. The inline modal gives the same "never leaves the portal" feel at SAQ A cost.

Cards unlock auto-pay. A card charge returns a reusable authorization — that's the payment_authorizations table — so the pre-departure milestone and post-arrival instalments can debit silently with consent. MoMo can't be tokenized; every MoMo payment is a manual prompt.

Under the hood — reuses today's settlement path

No new settlement logic: verify + webhook + pdfEngine receipts all stay exactly as they are.

MoMo · portal → POST /me/invoices/:id/momo-charge {phone, provider}
→ api → Paystack POST /charge (server-side, secret key)
→ client polls → GET /me/invoices/:id/momo-status?ref=PS-… (pending → success/failed)
→ existing → settleInvoicePayment → receipt PDF → notification

Card · portal → PaystackPop.setup (public key from /me/paystack-public-key)
→ callback → existing POST /me/invoices/:id/paystack/verify {reference}
→ if authorization.reusable → captureAuthorization (the table you just added)

Safety · the webhook + verify stay the source of truth — the UI never trusts its own callback

What changes for the client

Today: click Pay → full redirect to checkout.paystack.com → pay → redirect back → portal re-syncs. Two page loads, an unfamiliar domain mid-journey, and a broken session if the client closes the tab.
Proposed: click Pay → sheet opens inline → MoMo prompt on their phone → the same page flips to Paid. Card users see a modal, never a redirect. Receipt + invoice links are right there on the success state.
