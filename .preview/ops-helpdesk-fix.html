Helpdesk — the fix

Three things are wrong today: (1) staff can't start a conversation — the page has no create control and the ops API only makes staff↔staff threads; (2) the page is gated on the chat module while it lives under helpdesk, so some roles get a silently empty queue; (3) a redundant /chat page duplicates the floating CommunicationHub. This is the corrected design.

Waiting for clients to write first. There is no way for staff to open a thread.
FAIL 1 — cannot create EnterpriseHelpdesk.tsx has no create control at all, and the ops endpoint POST /chat/conversations only builds staff↔staff threads (direct/group/entity — it takes participantOpsUserId, never a clientUserId). Client threads (support/case/stage/applicant) are only born in the client portal via /me/communication/route. Ops can only ever reply — never initiate. FAIL 2 — wrong gate the page loads data only if roleCanAccess(role,"chat") but it sits under module="helpdesk", and every /chat/* API requires requireModule("chat") server-side. A role with helpdesk-but-not-chat → 403 → swallowed by forbiddenRef → empty queue, zero error shown. FAIL 3 — silent failure useChatConversations catches the 403, sets forbiddenRef, returns — the page renders an empty queue with no explanation. "Nothing is working" because nothing tells you why. FAIL 4 — duplicate surface /chat (ChatPage, full-page staff messaging) duplicates the floating CommunicationHub already mounted on every screen. Two places doing one job.
What staff actually need: a walk-in calls, a WhatsApp message arrives, a client emails — the first contact is often staff-initiated, not client-initiated. The current design only ever replies. The queue can sit empty forever while the phone rings.

Remove the Chat nav item + page. Staff↔staff messaging already lives in the floating CommunicationHub (bottom-right launcher on every screen — presence, directory, DMs, group threads). A full page for it is redundant. /chat?conversation=… redirects to /helpdesk?id=…. Notifications that deep-link to a thread keep working; staff-DM links open the CommunicationHub instead (the bell already intercepts them). Helpdesk owns all client communication — client threads, replies, internal notes, ownership, lifecycle. One surface, one queue.

The API gap this needs: today createConversationSchema accepts only participantOpsUserId(s) — no client. Add an ops-side create: POST /chat/conversations extended with { clientUserId, linkedEntityType?, linkedEntityId?, stageKey?, initialMessage }, reusing the portal's findOrCreateConversation logic — one thread per client per context, idempotent. If an open thread already exists for that client+case, join it instead of forking a second. "Regarding" picks the thread type: General support → support; Case → case linked to the application; Stage → stage with stageKey. Same taxonomy the portal uses, so the client sees one continuous thread. Deep link: /helpdesk?new=1 opens the sheet; ?client=<id> pre-fills the picker (from the client record pane). Staff↔staff stays in the hub. This sheet is only for client threads — DM a colleague via the floating CommunicationHub.
