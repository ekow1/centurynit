Ops · proposal for review

Cases · Clients · Consultations · Live meetings

Four pages, one review. They already share a spine — CaseScaffold list+detail — but each has drifted in its own direction: three different filter widgets, two selection models, one page that polls every 10 seconds, and a meetings page that can only show what is live right now. The theme of every change below: the list should answer "what needs me" before you open a record — and every control should be a URL, a keyboard, or a chip, consistently.

5a · Case detail — the audit first

Before the redesign: what the pane actually is today, line by line — what's load-bearing, what's dead weight, and what's quietly wrong.

Anatomy — top to bottom

BlockWhat it isFinding
Flash linesactionSuccess/actionError — bare <p> above the headerNot announced. No role="status"/role="alert" — screen readers never hear "Consent recorded". Also survives a record switch: change cases within the 4s window and the success from the previous case shows on the new one.
CaseHeader cn-caseName + ref + portal-stage pill + History button; facts <dl>: Stage, Branch, Consultant+Handler…, chapter officers, Country, Programme; mailto/tel linksTwo layout systems fight. The stylesheet defines cn-case__facts as flex; the JSX overrides it inline to a grid — dead CSS, and the override is a lint-warning inline style. Facts run 6–8 rows deep in one column — no visual hierarchy between "who is this" and "who works it".
CaseStateLine cn-stateDerived pill (Active / New / Needs attention / Completed) + facts: consent date, deposit, opened-from-consultationGood — keep. State is read from what happened, never set by hand. Minor: "New" is the pill for paused and declined too — a declined case wearing "New" misleads at a glance.
CaseTodo cn-todoNumbered next-actions — handoff gate, consent gate, advance button, then tasksForApplication items, each with its clearing control; waiting-on rows hollow; blockedBy lineGood bones, flat hierarchy. Every item gets the same weight — "place a visa officer" and "upload a transcript" look identical. The single most important action deserves a headline; the rest can collapse. Also: items are recomputed per render — fine — but tasksForApplication runs again for every row in the list above, so the work is duplicated across the page.
SheetsApplicationAssignSheet, HistorySheet, reason sheet (consent/decline)Good. History lazy-loads only when opened; reason sheet replaces a prompt() properly. Keep as-is.
CaseSpine cn-spineChip tablist: Overview · I–V chapters · hardcoded "VI Complete" · Money · Docs — chips styled by state (passed/now/locked)Three vocabularies in one control. Numerals (I–VI) are journey language; "Money/Docs" are views; "Overview" is neither. Passed/now/locked differ only by border style — a dashed vs solid 1px border is the whole signal for "you cannot click this". Not a real tablist: role="tab" chips have no arrow-key nav and no aria-controls→tabpanel linkage. The VI chip is aria-hidden, so screen readers never hear the journey's end.
Tab bodies8 bodies, ~3.4k lines — Overview (profile fact groups), Consultation, Enrolment, Applications, Visa, Departure, Money, DocumentsSound, out of scope here. Each is a chapter's workbench; the audit's changes are all in the frame around them.
